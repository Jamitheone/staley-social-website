Module 00

Set up your machine

You need three things: a computer, a terminal, and an AI coding tool. That's it. If the word "terminal" makes you nervous, good. By the end of this module it won't.

The stack, and what it costs

  • Your computer (Mac or Windows). Nothing special. What you already own is fine.
  • The terminal. On Mac it's an app literally called Terminal. On Windows, install Windows Terminal from the Store. It's a text box where you type commands instead of clicking buttons. That's the whole mystery.
  • Claude Code. This is the AI that writes, runs, and fixes code by talking to you. It's what ARIS is built on. Roughly $20/month to start, and you can do a lot on the entry tier.

Total to start: the price of one AI subscription. You can build real, deployed things at that level before spending another dollar.

Getting Claude Code running

Open your terminal and install it (the current one-line install command is on claude.com/claude-code, I'm pointing you there instead of pasting a command that'll be stale in a month). Then type claude and hit enter. You're in. It'll ask you to log in the first time.

The only terminal commands you actually need

cd my-folder      # "change directory" — go into a folder
ls                # list what's in the current folder
mkdir projects    # make a new folder called projects
claude            # start the AI

That's genuinely most of it. When you don't know a command, ask Claude Code itself. "How do I get back to my home folder?" is a valid thing to type at it.

Build this now

Make a folder called operator, cd into it, run claude, and type: "Explain what folder we're in right now and what's in it." You just had your first working session. That's the whole loop, everything else is bigger versions of this.

Module 01

How to actually vibe code

Vibe coding is not "the AI reads your mind." It's a conversation loop, and there's a skill to running it well. Master this and everything else in the course is just applying it to bigger targets.

The loop

  1. Describe the outcome, not the code. "I want a page that shows my daily tasks in a list" beats "write a React component with a useState array."
  2. Let it work. It'll write files, run things, show you results.
  3. Look at what came back. Did it do the thing? Run it and see.
  4. Correct in plain English. "The list works but I want newest on top" is a complete, useful instruction.
  5. Repeat until it's right.

How to describe what you want

The gap between a bad result and a great one is almost always the prompt. Three habits that fix 90% of it:

  • Give context first. "I'm building a personal dashboard. It's just for me, runs on my laptop." Now every answer is aimed correctly.
  • Say what "done" looks like. "Done means I can open it in my browser and see today's date." A clear finish line means it knows when to stop.
  • One thing at a time. Don't ask for ten features in one message. Ask for one, verify it, then the next. This is the single biggest quality lever.

When it breaks (it will)

Errors are not failure, they're information. When something breaks: copy the error and paste it straight back to the AI with "this broke, fix it." You do not need to understand the error. That's the entire trick that makes non-coders dangerous now. Read the error only well enough to notice if it's saying the same thing twice, which means the current approach is stuck and you should say "try a completely different approach."

The rule I live by

If it fails the same way two or three times, stop iterating and change the approach entirely. Repeating a broken plan louder never works. This one rule will save you more time than any prompt trick.

Build this now

Ask Claude Code to build "a single HTML page that shows a random motivational quote and a button to get a new one." Get it working in your browser. Then change one thing about it with a plain-English instruction. You just ran the full loop, including a revision.

Module 02

Ship something real, today

Nothing builds belief like seeing your thing live on the actual internet with a URL you can text to a friend. We're doing that in this module, before we go any deeper.

What we're shipping

A one-page personal site. A link-in-bio, a landing page, a "here's what I do" page. Small on purpose. The point is the deploy, not the page.

The move

  1. Tell Claude Code: "Build me a clean one-page personal site with my name, a short bio, and links. Plain HTML and CSS, no framework." Iterate until you like it in your browser.
  2. Then: "Deploy this to the internet for free and give me the live URL." It'll walk you through a free host (Vercel and Netlify both have generous free tiers and both can deploy a static page in under a minute).
  3. Open the URL on your phone. That's the moment it clicks.
Gotcha from experience

Deploy tools sometimes print a scary-looking error and still succeed. Before you panic, actually open the live URL. Half the time the "error" was noise and your site is already up. Always verify the real URL, never trust the console alone.

Build this now

Ship the page. Get a real URL. Send it to one person. Done is a link you can share, nothing less.

Module 03

Give your AI a memory

Here's the difference between a chatbot and an assistant: memory. A chatbot forgets you the second you close the window. ARIS remembers who I am, what I'm working on, and every lesson it's already learned. This module is the single most important idea in the whole course.

The CLAUDE.md pattern

Claude Code reads a file called CLAUDE.md automatically at the start of every session. Whatever's in it becomes standing context. This is your AI's long-term memory, and it's just a text file you control.

Put in it the things you'd have to re-explain every time:

# Who I am
Name: [you]. I go by [name]. Talk to me directly, no fluff.

# What I'm working on
Building a personal AI system. Current focus: [x].

# Rules
- Always verify before telling me something is done.
- Ask before doing anything I can't undo.

Now every session starts with the AI already knowing all of that. You stop repeating yourself. That's the whole win, and it compounds.

Memory that grows

The next level: a memory folder, where each fact lives in its own small file, plus one index file the AI reads first. When the AI learns something worth keeping ("this deploy trick failed, here's what worked"), it writes a new memory file. Over weeks, your system gets genuinely smarter about your world, not just the world in general.

Why this matters more than it looks

Every correction you save today is a mistake your AI never makes again. Memory is how a generic tool becomes your tool. This is the mechanism behind everything impressive about ARIS.

Build this now

Create a CLAUDE.md in your operator folder. Write five lines: who you are, what you're building, and three rules for how the AI should behave. Start a fresh session and ask "what do you know about me and this project?" Watch it answer from the file.

Module 04

Build your first agent

Up to now it's been you and one AI in a conversation. An agent is a specialized worker you hand a focused job to, with its own fresh attention. Instead of one assistant juggling everything, you get a team.

Why agents beat one long conversation

When a single session tries to do too much, quality drops. It loses the thread, gets lazy, drifts off goal. A sub-agent gets a clean context window and one job, so it stays sharp. Give the researcher one task: research. Give the writer one task: write. Each does its one thing well.

When to use one (and when not to)

  • Use an agent when a task is self-contained and you can describe the finished result. "Research this company and give me back five facts." "Write three versions of this email."
  • Don't bother for quick one-off things or tightly connected steps where each depends on the last. The overhead isn't worth it. Laziness is a virtue here, spin up an agent only when it earns its keep.

How you actually do it

In Claude Code you just ask: "Spin up a sub-agent to research X while we keep working on Y." It handles the mechanics. The skill is in scoping: give the agent a crisp goal, the context it needs, and a clear description of what to hand back. A vague agent is a useless agent.

Build this now

Pick a real task with a clear output, like "research the top three tools for [thing I care about] and return a one-line verdict on each." Have Claude Code run it as a sub-agent. Notice you got a clean answer without cluttering your main thread.

Module 05

Design a loop that runs itself

This is the idea that turns a tool you sit at into a system that works while you sleep. My rule: the unit of work is a loop, not a prompt. Stop prompting the AI over and over. Design loops that prompt the AI for you.

The six parts of every loop

If you can't fill in all six, it's not a loop yet, it's a wish. Every real one needs:

  1. Trigger — what starts it. A time (every morning at 7), an event, or a condition.
  2. Action — what it does when triggered.
  3. Oracle — the outside truth that tells you if it's actually working. Not a vibe. A number: replies received, dollars in, errors down. This is the part everyone skips and it's the most important one.
  4. Memory — what it remembers between runs so it doesn't repeat itself.
  5. Output — what it delivers. A text to your phone, a file, a posted thing.
  6. Exit — when it stops or hands back to you.

Making it run on a schedule

On a Mac, the built-in scheduler is called launchd. On Windows it's Task Scheduler. You don't need to learn either by hand. Tell Claude Code: "Set this script up to run every morning at 7am and text me the result." It writes the schedule config for you. My whole system is a stack of these.

The oracle rule

A loop with no oracle is a loop you can't trust. If you can't name the external number that proves it's working, you've built a machine that might be quietly doing nothing. Define the oracle first, before the action.

Build this now

Design one loop on paper, all six parts filled in. Easy starter: a morning brief. Trigger: 7am daily. Action: pull the weather and your calendar. Oracle: did the text arrive. Output: a text to your phone. Then have Claude Code build and schedule it. Wake up tomorrow to your first autonomous loop.

Module 06

Connect it to the world

A memory and a loop are powerful, but your AI is still trapped in a box until it can touch your real tools. This module gives it hands.

Three ways to connect anything

  • APIs. Most apps you use (your calendar, your CRM, Stripe, your email) offer an API, which is just a doorway for code to read and write data. You don't hand-write the API calls. You say "connect to my [tool] and pull my [data]," give the AI a key, and it does the wiring.
  • MCP. A newer standard that plugs pre-built tools straight into your AI. Think of it as an app store for AI capabilities. Search for one that fits, connect it, and your AI can now use that tool directly.
  • Browser automation. For tools with no API, your AI can literally drive a web browser: click, type, read the page. Slower and more fragile, but it means nothing is truly off-limits.
Handle keys like keys

API keys and passwords are exactly that, keys to your accounts. Never paste them into a public chat or commit them into code that goes online. Keep them in a separate, private config file. Your AI can use a key without it ever being exposed. Treat a leaked key like a lost house key: rotate it immediately.

Build this now

Connect one real tool. Easiest wins: your calendar or the weather. Ask Claude Code to "connect to [tool] and tell me [something from it]." The first time your AI reads live data from your actual account, the box is open for good.

Module 07

Point it at your business

Everything so far has been the toolkit. Now we aim it at the thing that pays you. These are the real patterns I run for my agency, generalized so you can point them at whatever you do for money.

The three automations that move the needle

  • Outreach. A loop that finds prospects, researches each one, writes a personalized message, and logs who got contacted so it never doubles up. Oracle: reply rate. The whole thing runs on a schedule and reports to you.
  • Content. A loop that takes an idea, produces the post or video, and queues it for a human (you) to approve before it goes out. AI does the heavy lifting, you keep the taste and the final yes.
  • CRM and follow-up. Speed-to-lead is a superpower. A loop that reacts the instant a lead comes in, and never lets a follow-up slip, will out-perform competitors who are "getting to it." Oracle: leads worked, follow-ups sent.

The one human checkpoint

Automate everything except the irreversible, outward-facing moment. Anything that sends, posts, spends, or deletes should pause for your yes. Everything up to that point runs itself. That single principle lets you automate aggressively without waking up to a disaster.

Where the money actually is

Notice you can run these for other people. Building your own system is step one. Running it as a service, or selling access to it, is a business. Module 9 is about exactly that.

Build this now

Pick the one automation that would save you the most hours this week and build a first version. Keep the human checkpoint on the send step. Even a rough version that saves two hours a week is a compounding win.

Module 08

Architect your own ARIS

You now have all the pieces: memory, agents, loops, connections. This module is how they snap into one coherent system instead of a pile of clever scripts.

The three-layer architecture

  1. Knowledge (bottom). Everything your system knows: your memory files, your notes, a searchable map of your own stuff. Every layer above pulls context from here.
  2. Workflows (middle). For any job too big for a single prompt, a structured multi-step process, often fanning out to several agents. This is where hard, multi-part tasks get done well.
  3. Loops (top). The autonomous monitors from module 5, each watching something and acting on a schedule, each with its oracle.

The magic is that they feed each other. A loop notices something, kicks off a workflow, which reads from your knowledge layer, and writes a new memory back down. That circulation is what makes a system feel alive instead of like a set of alarms.

Start small, let it grow

I did not build ARIS in a weekend. It started as one CLAUDE.md and one morning-brief loop, and grew every time I hit a task I was tired of doing by hand. That's the actual method: automate your own annoyance, one loop at a time. Don't try to design the whole cathedral up front. Lay one brick that's useful today.

Build this now

Sketch your own system on one page. What's in your knowledge layer? What's the first workflow? What are your first two or three loops? You don't build it all today. You build the map, then add one piece a week.

Module 09

Turn it into income

Meta-module. You're standing inside the exact playbook right now, because this course is a thing I built with the system the course teaches. Here's how to do the same.

The three ways to make money with this

  • Sell the outcome (done-for-you). Run your automations for clients. This pays the most per client but it's a job, you're the bottleneck. Sell it selectively and price it high.
  • Sell the access (software / templates). Package what you built so others can run it themselves. Lower price, but it scales because you're not doing the work each time. This is the passive engine.
  • Sell the knowledge (like this). Teach people to build it. Write it down once, sell it many times. Fastest to start because you already know the material, it's what you built.

The fastest path to a first dollar

Don't build for a hypothetical audience. Sell to the people already asking you. If people are messaging you "how did you do that," that's proven demand. Offer them the thing before you've built the whole thing. Presales validate the idea and fund the work.

  1. Write down what you'd teach on a call. That's your outline.
  2. Make a simple sales page and a payment link. Both can be built with the skills in this course, in an afternoon.
  3. Post it to the people already asking. Founding price, real urgency.
  4. Deliver, gather feedback, raise the price, add video. Improve the thing while it's already selling.
You already have the proof

The credibility that sells this is the working system you built in modules 0 through 8. Show the thing running. Nobody argues with a machine that's visibly doing the work.

Build this now
